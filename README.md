# SeleneLiveTV

仅保留 TV 直播功能的 Android TV 工程，最低支持 Android 9（API 28）。

## 当前版本

- 版本：`1.4.8-android9-bundled-fallback`
- 默认订阅：`https://gitee.com/daoshengtianxia/selene-iptv/raw/main/selene-sub.txt`
- 支持 Selene Base58 订阅：先解码 JSON，再读取 `lives.*.url` 对应的 M3U。
- 播放核心：`dev.jdtech.mpv:libmpv:1.0.0`（libmpv + FFmpeg）。
- 遥控器：↑ 上一台、↓ 下一台、OK 频道列表、菜单键进入订阅设置。
- 切台复用同一个 Activity/SurfaceView，使用 MPV `loadfile URL replace`。
- 本地缓存优先：有缓存时启动直接播放；6 小时内不访问网络；过期后后台静默刷新。
- 后台订阅更新失败不会打断当前缓存播放。

## 屏幕播放诊断

右上角会实时显示 MPV 播放阶段，用于定位直播卡顿位置：

- START_FILE：已开始打开直播地址
- FILE_LOADED：直播流已打开并完成基础解析
- VIDEO_RECONFIG：视频解码器/视频参数已经建立
- PLAYBACK_RESTART：实际播放已经启动或缓冲后恢复
- 缓存百分比、缓存秒数、视频/音频编码、分辨率、播放时间
- 若播放时间连续约 3.5 秒不增长，会直接显示“播放时间已停止”


## 自动恢复策略（1.4.5）

启动时优先使用本地已解析的 `live.m3u` 缓存。若缓存频道能正常播放，不依赖网络更新订阅。

当当前缓存频道出现以下异常时自动恢复：
- 已经 FILE_LOADED 且识别到视频参数，但约 6 秒仍未真正开始播放；
- 直播地址约 9 秒仍未打开；
- 连续缓冲约 12 秒；
- 播放过程中 time-pos 超过约 8 秒不增长；
- 播放开始前收到 END_FILE。

恢复顺序：
1. 先把当前频道切到软件解码再试一次；
2. 软件解码仍失败，则后台重新下载 Selene 订阅和最新 `live.m3u`；
3. 新订阅下载成功后写回本地缓存，优先按同名频道重新播放；
4. 更新失败则保留原缓存，不清空频道列表。


## 调试窗口交互（1.4.6）

- 返回键：频道列表打开时先关闭频道列表；否则若直播调试窗口可见，则只隐藏调试窗口，不退出应用。
- 切换频道：调试窗口重新显示。
- 真正连续播放约 2 秒且播放进度持续增长后，调试窗口自动隐藏。
- 若后续播放卡住并触发自动恢复，调试窗口会重新显示。


## 离线启动缓存（1.4.7）

- 成功获取直播列表后，同时写入应用内部文件 `playlist_cache.m3u` 和 SharedPreferences。
- 启动时优先读取内部文件缓存；文件无效时再读取 SharedPreferences。
- 只要本地存在可解析频道，启动时立即使用缓存播放，不先等待 GitHub/VPN。
- 缓存超过 6 小时时，延迟约 15 秒后台静默刷新订阅；刷新失败不影响当前缓存播放。
- 完全没有本地缓存时，才显示“本地没有频道缓存，正在首次加载直播订阅…”并联网获取。
- 调试窗口把“订阅缓存”和“直播源服务器”分开显示，避免把订阅网络问题与直播源卡顿混在一起。


## 首次安装无 VPN 兜底（1.4.8）

频道来源现在按三层优先级读取：
1. 应用内部文件缓存 `playlist_cache.m3u`
2. SharedPreferences 备份
3. APK 内置 `assets/fallback_live.m3u`

只要任意一层能解析出频道，启动时就先显示频道并尝试播放，不等待 GitHub。

订阅更新仍然使用原来的 Selene Base58 地址，但内部下载顺序对 GitHub Raw 做了优化：
1. `cdn.jsdelivr.net/gh/...`
2. `raw.githubusercontent.com/...`
3. GitHub raw 备用入口

这样不开 VPN 时更容易先拿到订阅，而直播频道播放仍直接访问频道自己的 URL，不经过订阅 CDN。

## 无人值守 TV 逻辑（1.5.0）

面向开机自动启动、用户只使用上下键换台的设备：

- 启动优先使用本地 `live.m3u`，不等待网络。
- 成功网络更新时同时缓存 `selene-sub.txt` 和最终 `live.m3u`，均保存到内部存储并保留 Preferences 备份。
- 旧版保存的 GitHub Raw 默认订阅地址自动迁移为 Gitee 默认地址。
- 阶段 1/4 超过约 9 秒未打开直播流，自动恢复。
- 阶段 2/4 超过约 10 秒仍未开始播放，自动恢复。
- 正常播放后若连续缓冲约 12 秒或播放时间超过约 8 秒不增长，也自动恢复。
- 恢复顺序：软件解码重试 → 后台刷新订阅（至少间隔 60 秒）→ 用同名新地址重播 → 仍失败自动切到下一个频道。
- 后台更新失败不会自动进入设置页，不要求用户处理。


## 国内 IPTV 播放恢复优化（1.5.1）

针对国内运营商/公网 IPTV 偶发首包慢、TS/HLS 关键帧等待、直播服务器瞬时抖动重新区分恢复阶段：

- 阶段 1/4：8 秒仍未 FILE_LOADED，先 stop 后原地址干净重连一次。
- 阶段 2/4：已打开流但 12 秒仍未建立视频解码，同样先按“源/网络问题”重连，不再误切软件解码。
- 阶段 3/4：视频解码器已建立但 8 秒仍未开始播放，才尝试软件解码。
- 正常播放后卡死：时间轴 8 秒不增长或连续缓冲 10 秒，自动进入恢复。
- 同一地址重连仍失败：后台刷新 Gitee 订阅并尝试同名频道新地址。
- 刷新后仍失败：自动切换下一个频道。
- MPV 直播缓存由 8 秒调整为 3 秒，并关闭初始缓存暂停，优先快速起播。


## 手动切台优先（1.5.2）

- 直播不流畅、直播源打不开、后台更新失败时，应用不再自动跳到下一个频道。
- 自动恢复仅限当前频道：原地址干净重连、必要时软件解码、后台刷新订阅并尝试同名新地址。
- 当前频道仍无法正常播放时，停留在当前频道并提示“网络较差或直播源暂时异常，请按 ↑ / ↓ 手动切换频道”。
- 用户始终保留上下键主动换台控制权。


## 连续切台稳定性（1.5.3）

针对“刚进入前几个频道能播，连续切几次后越来越容易卡住”：

- 人工上下切台不再直接 `loadfile replace`，而是先 `stop` 释放上一直播流，短暂等待后再加载新频道。
- 每次人工切台恢复到 `hwdec=auto-safe`，避免上一个频道的软件解码状态污染下一个频道。
- 若发出 `loadfile` 后约 5 秒连 `START_FILE` 都没有收到，判断为 MPV core/旧解码器状态异常。
- 此时只重建 MPV 播放器内核并继续当前频道，不自动切台。
- 仍保留原来的阶段1/2直播源重连、阶段3软件解码、Gitee订阅刷新逻辑。


## 已验证缓存 + 音频兼容（1.5.4）

针对“卸载重装后能播放，运行一段时间后又不稳定”：

- Gitee 后台更新得到的新 `live.m3u` 不再立刻覆盖本地已验证缓存。
- 新列表先作为候选；只有实际频道连续稳定播放约 2 秒后，才晋升为正式缓存。
- 候选列表如果播放失败，会被丢弃，保留上一份已验证可播放缓存。
- 这样下次开机不会因为一次后台更新把本来能播的缓存替换成当前网络下不可用的源。
- Android AudioTrack 固定为 48kHz / 16-bit / stereo，改善部分 Android 9 电视盒子的 MP2/AAC 破音兼容问题。


## 人工切台最高优先级（1.5.5）

- 取消自动软件解码切换，播放器始终使用 `hwdec=auto-safe`。
- 卡顿时只重连当前频道一次，再后台刷新订阅并尝试同名频道新地址。
- 仍失败只提示网络/直播源异常，不自动切台、不切软件解码。
- 播放控制命令不再全部排在同一个单线程队列里，避免某个 native `loadfile/stop` 卡住后导致后续 ↑/↓ 切台也完全无响应。
- 用户按 ↑/↓ 会立即使旧播放/恢复命令失效，人工切台优先。


## PlaybackController 状态机重构（1.6.0）

播放层改为更接近主流 TV/IPTV 播放器的分层：

- UI 主线程：只处理遥控器、频道提示和状态显示。
- PlaybackController：唯一负责 MPV 的 stop / loadfile / 当前频道重连，使用单独的专用控制线程串行执行，避免多个线程同时操作同一个 MPV 实例。
- libmpv：继续由其内部线程负责网络读取、解复用、音视频解码、AudioTrack 和 Surface/GPU 输出。
- SubscriptionWorker：Gitee 订阅、live.m3u、缓存更新继续走独立后台线程，不阻塞播放控制。
- Watchdog：若播放控制线程卡在 native 调用超过约 5 秒，会放弃旧 worker、创建新的控制线程代际，并重建 MPV 播放 session；旧任务即使迟到返回也会因为 generation 失效。
- MPV observer 增加 session id，旧播放器迟到的事件不会污染新播放器状态。
- 播放故障触发的订阅刷新绑定到当时的 playback generation；用户在下载期间手动换台后，旧刷新结果不会把频道再切回去。
- ↑/↓ 人工切台会清掉尚未执行的自动恢复任务，并生成新的 playback generation，因此用户操作永远优先。
- 不自动换台，不自动切软件解码；异常只重连当前频道、必要时重建播放器或刷新同名频道地址，最终由用户决定是否换台。
- Gitee 后台更新的新列表只有在“这份候选列表本身”实际稳定播放后才会晋升为正式缓存，避免健康旧流误把未验证列表写成好缓存。


## 稳定播放控制收敛（1.6.1）

针对 1.6.0 在虚拟机/弱设备上出现“切台卡死、虚拟机被拖死、无法播放”的问题：

- 移除“5 秒 watchdog 跨线程 destroy MPV”的激进恢复方式。
- 不再在一个 native command 尚未返回时从另一个线程销毁同一个 libmpv 实例。
- 人工切台不再先执行 `stop`，直接使用 mpv 标准 `loadfile <url> replace`。
- PlaybackController 仍保持单一专用控制线程，避免多线程同时操作 MPV。
- 连续 ↑/↓ 会清掉尚未执行的旧切台任务，只保留用户最后选择。
- 播放卡住时只显示“网络/直播源异常，请手动换台”，不再自动重连、自动重建播放器、自动软解或自动切台。
- Gitee/缓存更新仍在独立后台线程中，不阻塞播放控制。
- 当前 APK 仍面向真实 ARM Android TV/盒子（armeabi-v7a）；x86/x86_64 Android 虚拟机若进行 ARM native 转译，1080P libmpv 播放性能不能代表真实设备。


## 同频道多线路自动切换（1.7.0）

针对公网 IPTV 单一 URL 经常出现 `START_FILE` 后长时间没有 `FILE_LOADED` 的情况：

- selene-iptv 生成器现在每个频道最多保留 3 条不同 URL，优先来自不同上游来源。
- M3U 中同名频道会出现多条线路；APK 解析时自动合并为一个频道，不会在频道列表里显示重复频道。
- 播放当前频道时，如果当前线路连接/缓冲超时，不换频道、不切软件解码，只切换该频道的下一条备用线路。
- 所有备用线路都失败后才提示“当前频道线路异常，请按 ↑/↓ 手动换台”。
- 调试窗口显示当前线路编号，例如 `线路：2/3`。
- 某条线路真正播放成功后，会按频道保存为“上次成功线路”；下次启动同一频道优先使用这条线路。
- 用户 ↑/↓ 仍然拥有最高控制权，程序不会自动跳到其它频道。
